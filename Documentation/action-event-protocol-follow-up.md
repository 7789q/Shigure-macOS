# 动作事件协议 v6 后续操作

## 文档状态

- 目的：指导动作码错配修复后的部署、最小验证和 20 分钟以上实战验收。
- 当前协议：Fuyutsui 与 Shigure Runtime 使用协议 v6；运行时健康门禁校验同一 `Fuyutsui协议版本` 字段，二者不是独立版本号。
- 当前事件传输：固定动作事件队列 4 槽，协议块 504-519，每槽包含动作序号、技能码、状态码和 WoW 客户端失败原因码；目标身份序号位于协议块 520。
- 运行时详细日志：`~/Library/Application Support/Shigure/logs/runtime-detailed.log*`；日志只用于本机诊断，不进入仓库。
- 源码验证、实际应用包和待部署项统一见[当前交付状态](macOS/README.md#当前交付状态2026-09-10)；协议版本相同不能证明某个包已经包含最新代码修复。
- WoW 实战验收按本文后续步骤单独记录；普通施法成功样本不等同于整段确认链已无错配。

## 当前实现基线（2026-09-10）

- 普通技能保持一个待确认代次，只有明确更高优先级且获准抢占的动作才能替换；圣疗另保留独立确认代次，既不抹掉普通动作回执，也不以等待圣疗阻塞后续治疗。同一待确认圣疗不能换目标重投，并发匿名事件不冒认圣疗成功。
- 对适用当前目标门禁的技能，发送前重新扫描并校验窗口身份、目标类型、距离、死亡和正面状态，确认使用这次新快照。审判采用宏目标回退时不强制走当前目标预检，不能用无效当前目标阻断坦克目标回退。
- 资源或冷却变化只有在没有动作事件，或与当前待确认动作匹配时才能确认成功；不匹配的非匿名事件和只反映资源变化的冲突状态保持不确定，不能清除待确认动作。正义盾击共享神圣能量，禁止使用跨技能的通用延迟确认；必须观察盾击自身动作码 `11`，或满足专用匿名盾击回退（神圣能量下降、动作序号递增、动作码为 `0` 且状态成功）。
- 正义盾击的日志键位必须与生成 keymap 一致；神圣专精当前目标槽位为 `ALT-NUMPAD8`，出现 `SHIFT-F10` 等未生成宏槽位时视为插件/运行时资源混用，保持 fail-closed。
- 普通 GCD 技能不叠加确认后的固定 1500 ms 保持；奶骑和血 DK 队列窗口为 200 ms，其他职业默认 50 ms。非 GCD 技能保留重复发送保护。300 ms 是重试节奏，不能作为所有动作的固定重发间隔。
- 圣疗按 `UnitSelector.ResolvePlayerSlot` 校验独立自身血量。团本安全检查未通过时，最多重新评估一次其他动作，原圣疗双帧检查继续累计，不能因退让而直接绕过。
- 当前目标技能发送前会重新读取目标窗口；目标身份、类型、死亡状态和距离必须连续稳定，友方 NPC 统一使用目标类型 `152`。
- 当前仍未实现 WoW target GUID/目标代次与 Runtime 请求之间的 `intent_id` 闭环；有效到有效的快速换目标、手动施法与自动投递的同技能归因仍需 WoW 实战和后续协议升级验证。

## 1. 部署顺序

必须把 Fuyutsui 插件和 Shigure Runtime 作为同一个版本对部署：

1. 更新插件文件：`Fuyutsui/core/block.lua`、`Fuyutsui/core/player.lua`、`Fuyutsui/core/stateblocks.lua`、`Fuyutsui/main.lua`，以及它们依赖的同版本插件文件。
2. 更新 Shigure Runtime。运行时必须能够识别协议 v6，并读取 504-520 的固定动作事件队列和目标身份字段；本轮动作确认收紧也必须随 Runtime 一起更新。
3. 进入 WoW 后执行一次 `/reload`，等待插件握手和状态心跳恢复。
4. 重启 Shigure Runtime，确认旧插件或旧运行时不会被当作健康状态继续运行。
5. 只有以下条件同时满足时才认为逻辑已开启：协议版本匹配、状态心跳持续变化、目标类型有效、战斗时间有效、宏绑定状态有效。

不要只升级一侧。插件 v5 配旧 Runtime，或 Runtime v5 配旧插件，均应视为协议不匹配并保持 fail-closed。源码修复完成后必须重新打包，旧包不能作为新行为的验证对象。

## 2. 最小验证

### 2.1 单技能连续验证

选择一个不会触发特殊宏分支的普通技能，重复施放 20-50 次。每次只关注以下事实：

- 动作事件序号持续递增，或按协议允许的模数正确回绕。
- 同一事件的技能码、状态码和动作序号属于同一个队列槽。
- Runtime 只确认当前待确认动作，不把上一动作的迟到事件当成当前动作成功；资源/冷却变化也必须与当前动作匹配，冲突时保持不确定。
- 失败、取消、目标无效和超时在日志中保持不同原因，不被统一归为成功。

### 2.2 交错技能验证

准备两个技能 A、B，按 A-B-A-B 交替施放，并在其中穿插一次会产生迟到事件的技能。验收重点：

- 队列顺序与实际施放顺序一致。
- 迟到的旧技能事件不会替换当前待确认技能。
- 当前动作未确认时，不会因为另一条旧事件重复发送或错误清除待确认状态。
- 不再出现“日志显示技能 A，但动作码被识别为技能 B”的错配。

### 2.3 冲突与短窗口验证

在 GCD、移动、目标切换和目标死亡场景下分别验证：

- 冲突等待不能固定阻塞 1 秒；应使用当前队列窗口和短退避策略。
- 冲突期间只取消或替换不再有效的动作，不阻塞后续更高优先级动作。
- 目标死亡、脱战或会话结束时，待确认动作应在一个状态刷新周期内清理。
- 日志要区分 `conflict`、`cancelled`、`timeout` 和 `not accepted`，方便判断是调度问题还是 WoW 未接受动作。

## 3. 20 分钟以上实战验收

实战日志必须从同一场战斗或同一连续会话的开始位置读取到结束位置。滚动日志 `.1`、`.2` 等只能在确认时间边界后辅助拼接，不能把不同场次和历史日志直接合并统计。

以固定日志路径为准：

```sh
LOG="$HOME/Library/Application Support/Shigure/logs/runtime-detailed.log"
sed -n '1,200p' "$LOG"
```

验收时记录统计结果，不复制原始运行时日志到仓库：

| 指标 | 通过标准 |
| --- | --- |
| 会话边界 | 能明确识别战斗开始、结束、脱战和重载时间 |
| 动作发送 | 发送记录与实际需要的技能数量大致一致，无持续重复发送 |
| 动作确认 | 确认事件能绑定当前动作，不消费旧事件 |
| 错配 | 20 分钟实战中无动作码与技能码错配 |
| 冲突 | 有冲突时快速取消、替换或短退避，不出现固定 1 秒卡顿 |
| 超时 | 超时后有明确原因和有限重试，不形成永久阻塞 |
| 目标切换 | 目标变化不会把旧目标的迟到事件绑定到新动作 |
| 发送前目标复核 | 当前目标技能在发键前完成新扫描，目标窗口身份和目标类型/距离等字段未变化 |
| 会话清理 | 目标死亡、脱战、重载后没有残留待确认动作 |
| 健康门禁 | 协议、心跳、目标、战斗时间和宏绑定均有效后才发键 |

必须单独抽查：开战前几秒、第一次技能交错、连续移动、目标死亡前后、脱战后重新开战，以及 `/reload` 后的第一轮动作。这些位置最容易暴露旧状态、迟到事件和协议半更新问题。

## 4. 失败处理与回退

出现以下任一情况时，先停止把日志解释为“技能策略错误”：

- 协议版本不是 v6，或 504-520 队列/目标身份字段缺失。
- 心跳冻结、目标类型无效、战斗时间无效或宏绑定未就绪。
- 只更新了插件或只更新了 Runtime。
- 测试使用的是旧二进制，无法证明当前源码行为。
- 运行的是未包含本轮 Runtime 改动的旧应用包，无法证明当前源码行为。

处理顺序：

1. 保存时间范围、版本号、协议健康状态和错误计数；不要删除原始日志。
2. 确认插件与 Runtime 来自同一份构建结果，重新执行 `/reload` 并重启 Runtime。
3. 若仍失败，成对回退到上一个已知可启动版本，不混用新插件和旧 Runtime。
4. 回退后重新确认协议版本、心跳和发键门禁，再进行短时复测。

## 5. 根治动作码错配的下一阶段

当前 4 槽动作事件队列解决了“最新快照被覆盖”和“技能码、状态码、序号来自不同帧”的问题，但它仍然是状态协议，不能完全证明某次键盘请求就是某次 WoW 施法。

要从根源消除错配，后续应把动作确认升级为请求-响应模型：

1. Runtime 为每次投递生成单调递增的 `intent_id`。
2. 投递记录同时携带技能码、目标标识、发送时间和当前会话标识。
3. Fuyutsui 在可确认的玩家施法事件中回传 `intent_id`；无法确认时明确回传匿名或未知状态，不猜测绑定。
4. Runtime 只接受当前待确认 `intent_id` 的响应，旧会话、旧目标和旧代次响应全部丢弃。
5. 增加回放测试：乱序、重复、迟到、跨目标、跨会话和协议丢槽都必须保持不误确认。

在 `intent_id`、目标 GUID/代次和乱序回放测试完成前，本文的协议 v6 修复应称为“减少快照覆盖、按技能维护确认代次并携带失败原因码”，不要称为动作确认链路的最终根治。
