Shigure for macOS 由四层组成：

1. `Core` 保存配置、模块、协议解码、运行循环和用户数据规则。
2. `Platforms/Shigure.Platform.Abstractions` 定义目标窗口、权限、捕获、输入和按键输出合同。
3. `Platforms/Shigure.Platform.Mac` 使用 CoreGraphics、ApplicationServices 和 macOS 进程/窗口 API 实现平台合同。
4. `Apps/Shigure.MacUI` 通过 `Apps/Shigure.MacApp` 与 `Presentation` 组合业务能力和 Avalonia UI。

## 上游对齐边界

当前 macOS 分支保留自己的协议、Runtime、模块同步和 UI 行为，不以逐项复制上游为目标。为保持现有运行链路稳定，本轮明确暂不移植以下上游数据能力：

- `itemsList` 全量物品列表及 `ClassBlocks.items` 数据结构。
- 一键物品的通用规则、物品宏生成和对应 Runtime 动作路径。
- 独立物品数据库及其从数据源到模块、协议、UI 的完整链路。

现有模块继续使用已经验证的固定物品字段和 `/use` 宏路径。未来若重新评估，必须先设计兼容的数据版本和迁移边界，逐层验证模块、Runtime、同步工作副本和用户自定义职业 Lua；不得直接复制上游字段或覆盖现有 `Fuyutsui/class` 内容。

`Fuyutsui/`、`FuyutsuiDiGuaBridge/`、`config/`、`keymap`、`wow_process.txt` 与 `BundledModules/` 随版本作为只读基线进入应用包。运行时会在 `~/Library/Application Support/Shigure/runtime` 建立可升级工作副本，并在 `~/Library/Application Support/Shigure/module` 管理用户模块；同一内置模块 ID 发现包内版本更高时先备份再自动升级，跨 ID 的历史模块仍需命中已知官方旧哈希才升级，同版本或更高版本的用户模块保留。用户也可以在 APP 设置中指定本地模块源目录；指定后 APP 启动时优先从该目录同步，同模块版本更高或同版本内容变化时先备份再原子替换，无需重新打包 APP。

## Fuyutsui 协议升级

- 当前基线使用 Fuyutsui 1.2.1.15：`施法` 已拆分为 `施法(倒计时)` 与 `施法(正计时)`，施法时间以 `1 秒 = 10` 编码，并增加鼠标指向及首领 1-5 的单位状态。
- 运行健康协议固定使用状态索引 `502`/`503` 的 `Fuyutsui协议版本`/`Fuyutsui状态心跳` 字段，当前 Fuyutsui 协议版本为 `6`。Fuyutsui 每约 200 ms 在周期刷新完整成功后更新心跳；生产运行时只有在版本匹配且心跳持续变化时才评估并发送逻辑。字段缺失、版本不匹配或心跳冻结会保持逻辑等待并禁止按键发送。
- 神圣圣骑士额外输出 `公共冷却时长`、`公共冷却剩余`、`圣洁鸣钟预计可用`、`DiGua桥接就绪` 及玩家动作序号/技能/状态。`圣洁鸣钟预计可用` 表示鸣钟剩余冷却不晚于当前 AOE 预计美德时点；无法取得可信时间或冷却值时保持为假。GCD 字段单位为 10 毫秒；桥接握手和动作字段用于发键门禁与施法确认。
- `公共冷却时长`按 WoW GCD 冷却对象的 `duration / modRate` 输出，`公共冷却剩余`使用同一速率计算；普通 GCD 技能只受实际 GCD 和队列窗口限制，非 GCD 技能才使用确认后的重复发送保护。
- 工作副本和模块条件中的旧 `施法` 字段会统一迁移为 `施法(倒计时)`，随后从 `Fuyutsui/class` 重新生成 `config`；模块中依赖旧时间尺度的阈值仍需人工复核。缺失字段参与比较时不命中规则，避免 `未知字段 != 0` 阻断整个模块。
- 玩家光环按 SpellId 观察当前存在状态，不限制施法来源；目标和焦点光环仍只观察玩家施加的同名效果。
- 治疗吸收由独立的 6 行像素条传输，单元宽度按物理像素对齐；奶骑生命字段不再混入未完成读条的预估回血，`UNIT_HEALTH` 即时更新并以团本四帧轮询兜底。解码吸收值不会覆盖组员生命值。治疗缺口统一按“缺失生命百分比 + 治疗吸收百分比”逐单位计算。
- AOE 预警固定使用 `AOE事件类型` 与 `AOE事件阶段` 两个状态字段。DiGua 在受保护环境中可能输出 `spellID=0`；`Fuyutsui/core/diguabridge.lua` 从 DiGua 调用时间轴 API 的原始输入重发带真实读条 Spell ID 的事件，避免事件派发后的受保护字段丢失，并作为唯一机器可读映射注册表。兼容目录 `FuyutsuiDiGuaBridge` 只调用该入口，不复制机制清单。兼容性按所需 API/数据能力检测，版本字符串只用于诊断。
- 桥接由已经加载的 Fuyutsui 本体在 `/reload` 后按关键时间轴 API 能力初始化；DiGua 缺失、关键 API 不可用、未知图标、`spellID=0`、受保护值或只有语音时均只进入资源预留。检测到的 DiGua 版本仅用于诊断，不作为硬编码门禁；该实现不会改写 DiGua 文件。
- 普通 AOE 在匹配读条剩余 1 秒内进入美德窗口。吸奶盾只有在技能身份明确时，才按实际读条结束时点加 2 秒进入阶段 3；结束时间受保护时，可用可读 DurationObject 或匹配成功终态补足时点。姓名板 11.7 秒倒计时只预留资源，不能单独打开阶段 3 或阶段 5；实际多人吸收满足门槛时走独立反应式入口。现役链路、禁止改动项和验收标准见[美德道标与吸奶盾现役实现](../holy-paladin-virtue-implementation.md)。
- 中断、失败、取消和超时按[共享 AOE 契约](../holy-paladin-virtue-implementation.md)处理；取消预警不能作为施法成功证据。DiGua 对原事件调用 `CancelScriptEvent` 时，兼容桥会向重发事件传播取消。
- 吸奶盾在 `virtueReadyAt` 后最多保留 10 秒执行窗口；只有美德已确认、实际吸收曾为正且连续两次归零时才提前结束。吸收不可读时保留到窗口超时。
- `/fu aoedebug` 保留开关，但当前 Lua `DebugLog` 没有输出实现；不要把它当成可取得逐次施法明细的日志源。现有证据来自 App 的运行日志与已传输的诊断计数，未进入协议的事件详情保持未知。
- 普通 AOE 保留 0.5 秒内姓名板读条与预警的相关性匹配；吸奶盾拒绝仅凭时间接近识别受保护 Spell ID。可用的 DurationObject 只提供时间信息，不能代替吸奶盾技能身份。App 日志会区分原始读条、受保护字段和受保护匹配，并在协议失效或 `/reload` 后重新建立静默基线。
- 团队识别统一使用 `UnitInRaid("player")`：团本读取 `raid1..raidN`，小队读取 `player + party1..partyN`。协议固定按成员步长最多解析 30 个槽位；`可治疗` 单独表达单位当前是否可有效治疗，超距、死亡或不可协助的成员不会进入治疗选择；距离状态同时保留用于诊断和其他目标门禁。
- 友方非玩家目标使用目标类型 `152`，供模块进入当前友方 NPC 独占治疗路径。
- 友方 NPC 无论通过当前目标还是 `boss1..boss5` 单位槽位暴露，都先归一为目标类型 `152`，避免副本 NPC 被编码为槽位类型 `146` 后无法命中 NPC 治疗规则。
- 用户职业配置和生成配置可以保留本地差异；若 `Fuyutsui/main.lua` 或协议核心 Lua 存在本地冲突，Mac UI 与命令行都会禁止插件同步和运行时启动，并报告具体路径，避免混用新旧协议。
- 仅看到“界面已就绪”“模块匹配”或“逻辑已开启”不能证明游戏状态已被正确识别；排查时必须同时看到协议版本、心跳变化、战斗时间、目标类型/生命值和宏绑定状态，并确认日志出现有效目标或明确的阻断原因。
- 有效性状态仍会暂停动作，但状态码 `3`（乘骑）、`4`（聊天输入框）和 `6`（施放坐骑）不再显示屏幕提示；死亡、饮水和扫描未就绪仍显示故障原因。
- Mac 快捷控件固定忽略游戏 UI 缩放，位置按默认缩放基准迁移；鼠标中键通过全局 `GLOBAL_MOUSE_UP` 切换无限爆发，不能在局部按钮事件中重复触发。

## 单位目标路由

- 目标类型协议中，普通敌人为 `1`，精英或等级高于 90 的敌人为 `91`，首领为 `92`；队伍外友方玩家为 `151`，队伍外友方 NPC 为 `152`。敌对技能应判断 `1..99`；死神印记副本外允许所有有效敌对目标，副本内才限制为目标类型 `>90`，不得依赖旧的单位索引编码（如 `51`）。
- `Fuyutsui/core/classmacros.lua` 是职业宏路由模式的权威源。`selector-target-v1` 先为每个治疗技能生成选择键，再复用 30 个单位目标键；`config/` 和 `keymap/` 由同一配置生成，不维护第二份手写映射。
- `selector-target-v1` 的 1 号在小队/单人时对应玩家，在团队时对应 `raid1`；团队玩家位置由 `队伍类型` 的 1–40 编码与 `UnitSelector.ResolvePlayerSlot` 统一解析，不能固定视为 1 号。自动治疗目标仍限于 1–30；0 和 31–35 是静态/保留目标标识，不能与团队成员序号混用。
- 每次建立运行工作副本后都会从活动的 `Fuyutsui/class` 与 `Fuyutsui/core/classmacros.lua` 重新生成派生 `config` 和 `keymap`；旧版单键映射不会作为本地冲突继续覆盖新版路由，Lua 自定义则由同一生成链同步到 Mac 与 WoW。
- 静态宏中的 `[@tanktarget]` 是 Fuyutsui 扩展目标。审判先尝试当前敌对目标，再回退坦克目标；其他使用该扩展的技能先取坦克目标，再回退当前目标的目标和当前敌对目标。队伍成员或职责变化时重新生成。
- 奶骑正义盾击不使用上述坦克目标回退：模块仅在当前目标为敌对单位且 5 码内时发送直接当前目标宏，不依赖副本内受限的正面 API，避免因客户端 API 限制导致永不释放。
- 运行时把一次模块动作解析为有序按键序列，并在选择键释放后等待 50 毫秒再发送目标键。发送前会一次性校验完整序列，任何无效按键都不会产生部分施法；当前目标技能在发键前还会重新扫描并校验目标窗口身份、目标类型、距离、死亡和正面状态。
- WoW 端使用 `SecureHandlerClickTemplate` 在安全环境中更新目标宏文本，不通过受保护的脚本点击转发。`Fuyutsui/core/macro.lua` 因此属于协议核心；它与应用基线冲突时必须阻止混合版本运行。
- 模块依赖保存宏路由模式。导入模块时只补充本地缺失内容，路由或既有技能定义不同仍保留本地并报告冲突。

## 捕获与权限

- 生产扫描使用 CoreGraphics 捕获目标顶部协议窄带，并保留物理像素 RGB。
- 屏幕录制用于读取目标窗口；辅助功能用于输入监听和定向按键发送。
- 触发键同时读取当前按下状态并消费 CoreGraphics 按下脉冲，避免短促键盘或侧键点击落在扫描间隔之间；键盘自动重复不会生成新脉冲。
- 同一触发键的多个离散脉冲会逐个消费，不再被单个布尔锁存合并。
- CoreGraphics 事件监听在曾成功启动后若意外退出，会在下一次脉冲采样时重建，避免长时间运行后退化为仅依赖瞬时按下状态。
- 圣疗术发送前要求同一危急目标连续两帧不高于 30%，并使用独立自身生命值及玩家自身自律校验玩家槽位。WoW 12.1 不提供可供逻辑读取的队友特定有害光环身份，因此不得用队伍 `HARMFUL` 槽推断自律；队友资格由 WoW 拒绝非法施法，并以圣疗冷却变化确认成功。
- 奶骑与血 DK 的普通 GCD 排队窗口均为 200 ms，其他职业默认 50 ms；300 ms 是重试请求节奏，不是血 DK 的 GCD 窗口。投递后等待确认，不按固定节奏重复发送未确认动作。读条打断仍受技能白名单限制；圣疗独立确认与具体归因规则见[动作事件协议](../action-event-protocol-follow-up.md)。
- 当前协议仍没有 WoW target GUID/目标代次与 Runtime 请求之间的 `intent_id` 闭环；快速换目标、手动施法和自动投递的同技能归因仍需 WoW 实战验证，不能把本地状态回放称为最终施法确认。
- 奶骑大秘境的输出和圣能消耗条件以模块 JSON 为准；团本另有美德临近就绪时的资源预留和低圣能鸣钟优先分支，不能套用同一张优先级表。类型 2/阶段 5 是美德前最后 GCD 保护窗：运行时在进入时作废既有普通 GCD 待发送动作，并统一阻止新的普通 GCD，避免模块规则遗漏或顺序变化抢占时点；圣疗术、非 GCD、驱散和受伤友方 NPC 治疗例外。
- 大秘境清洁术保持原自动规则；团本默认关闭自动清洁术、保留手动键位，显式启用后还需满足战斗和血量门槛。团本奶骑光环槽使用 `HARMFUL|RAID` 与已学会的驱散类型共同过滤，不能仅凭减益类型推断可驱散。
- 治疗吸收正值需要连续两帧确认后才参与规则评估，零值立即清除，且保留 1% 至 100% 的精确数值；吸收变化会生成去重诊断。
- 运行日志使用虚拟化逐行列表并固定保留最近 2000 行，避免日志增长导致整块文本反复重排。
- 战斗快照、运行状态和运行日志的 UI 刷新具有独立异常边界；单个监控视图失败时只停止该类界面更新，不中断按键运行时，并把首次完整异常写入 `~/Library/Application Support/Shigure/logs/runtime-ui-errors.log`。中央状态提示与按键发送共用配置目标的 macOS 前台进程判断，只在 WoW 位于系统前台时显示；浮动状态条不受此限制。状态提示窗口已显示时只更新内容，不重复调用窗口显示。
- 权限请求只能由用户显式触发；状态检查不得弹出系统提示。
- 捕获与诊断默认不保存画面，显式导出只允许 PPM 诊断文件。

## 签名与发行

- `ensure-local-signing-identity.sh` 只创建本机开发身份，用于保持本地 TCC 主体稳定。
- 本机开发身份的 SHA-1 指纹固定在 `~/Library/Application Support/Shigure/local-signing-identity.sha1`；证书丢失、替换或出现多个同名身份时打包必须失败，不得静默轮换。
- `build-app.sh` 不允许 ad-hoc 签名。日常测试固定覆盖并启动 `/Applications/Shigure.app`，避免临时包名和运行路径持续变化。
- 本地签名的 designated requirement 固定为“证书根 + 标识符”，禁止绑定 `cdhash`；外层应用和 `Shigure.MacUI` 的标识符是 `com.arasaka.shigure.mac`，执行捕获和按键的 `Shigure.MacApp` 必须保持兼容标识符 `Shigure`。三者任一身份或 requirement 漂移都会使已有 TCC 授权失配，打包脚本必须在签名后验证它们。
- 修改 `Packaging/macOS/*.sh` 后必须运行 `bash -n Packaging/macOS/*.sh`，并用 `codesign --verify --deep --strict` 及 `codesign --display --requirements -` 检查实际生成包；本地 Terminal 的权限探针结果不能替代从 Launch Services 启动的 GUI 验收。
- 对外发布必须使用 Developer ID Application、Hardened Runtime、最小 entitlement、公证、staple 和 Gatekeeper 验证。
- Sparkle 私钥只能由钥匙串读取；仓库只保存版本、公开下载地址入口和公开密钥配置位置。
- `prepare-release.sh` 只准备本地产物，不创建 GitHub Release，也不上传文件。

当前公共仓库只发布源码，没有 Developer ID 签名、公证或 Apple 审核的二进制版本。

## 模块与诊断

- `BundledModules/` 是官方随包模块的事实来源；启动时补装缺失模块。同一内置模块 ID 按语义版本比较，包内版本更高时先备份再升级，跨 ID 的历史模块只对 SHA-256 精确匹配的已知官方缺陷版本升级。
- 奶骑当前治疗规则以 `BundledModules/` 为准，团本差异见[团本实现文档](../holy-paladin-raid-virtue-implementation.md)，AOE/吸奶盾状态机见[共享协议](../holy-paladin-virtue-implementation.md)；[早期治疗设计](../holy-paladin-healing-optimization-design-2026-09-06.md)仅供背景与待验证方案参考。
- 扫描失败提示使用跨 Space、全屏辅助窗口，并在持续故障时补显；浮动条同时显示具体失败原因。
